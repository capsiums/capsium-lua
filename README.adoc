== Purpose

The Capsium Nginx extension is an OpenResty/Nginx reactor that serves
Capsium packages (`.cap` files, ZIP format) directly through Nginx with
Lua. Drop a `.cap` file into the packages directory, optionally configure
a mount point, and the package is served — extracted on demand, verified,
and routed.

== Features

* *Single module tree* — one framework-agnostic core (`lib/capsium`) plus a
thin Nginx glue layer (`lua/capsium`); no duplicated logic
* *Integrity verification* — SHA-256 checksums from `security.json` are
verified at extraction; tampered packages are rejected with 5xx and reported
by `content-validity`
* *Digital signatures (§6a)* — when `security.json` declares
`digitalSignatures`, the RSA-SHA256 signature is verified against the
canonical signed payload at extraction; non-matching packages are rejected
* *Encrypted packages (§6b)* — the `metadata.json` + `signature.json` +
`package.enc` layout is detected at extraction; the RSA-OAEP-SHA256-wrapped
DEK is unwrapped with a configured private key and the inner zip is
AES-256-GCM-decrypted, then handled like a plaintext package
* *Layered storage (§5a)* — `storage.layers` overlay semantics: top-to-bottom
first-hit resolution, `.capsium-tombstones` deletions resolve 404, private
layers hidden from dependent packages (serving is read-only)
* *Composite packages (§4a)* — `metadata.dependencies` resolve against a
package store (newest satisfying semver); dependency content mounts
read-only with exported-only visibility; route inheritance honors `remap`,
`responseRewrite` (body/headers), `responseHeaders`, `requestHeaders`
* *Authentication (§4b)* — `authentication.json` basicAuth (htpasswd:
apr1/{SHA}/bcrypt/crypt) and OAuth2 authorization-code + PKCE against
configurable endpoints with signed-cookie sessions; dataset-route
`accessControl` maps to 401/403
* *Static registry pull* — mount sources may be `capsium://<guid>`
references resolved against a static registry (a directory or https
base URL with an `index.json`): newest satisfying semver, sha256-verified
install into the package store, store reuse across restarts
* *Reactor + per-package introspection* — `GET /introspect/status`,
`/introspect/config` (redacted), `/introspect/metrics` and
`GET /package/<name>/status|metadata|logs` (07-reactor)
* *Manifest-driven routing* — routes are auto-generated from `manifest.json`
per the Capsium routing rules (dual HTML routes, index, dataset routes)
* *Canonical + legacy schemas* — metadata, manifest, routes, storage and
security files are accepted in both the canonical forms and the legacy gem
forms (normalized on read)
* *Config-driven mounts* — packages are mounted by Host/path prefix from
`config.json`; every package is also auto-mounted at
`/capsium/<package-name>`
* *Cold-start introspection* — `/api/v1/introspect/*` endpoints lazily
extract and load packages on demand
* *Per-mount headers and CORS* — custom headers and full CORS handling
(including preflight) per mount

== Architecture

.Module structure
[source]
----
lib/capsium/                  Framework-agnostic core (the rock)
├── utils.lua                 Pure helpers (tables, JSON files, base64)
├── mime.lua                  MIME type detection (text/javascript per RFC 9239)
├── csv.lua                   Minimal CSV parser (dataset support)
├── crypto.lua                Crypto facade (lua-resty-openssl): RSA-SHA256
│                             verify, RSA-OAEP-SHA256 unwrap, AES-256-GCM
├── semver.lua                Semver comparison + range matching (§4a)
├── registry.lua              Static registry pull: index.json resolution,
│                             sha256-verified install (local dir + https)
├── log_buffer.lua            Per-worker ring buffer for /package/<name>/logs
├── reactor.lua               Reactor core: package management + introspection
├── package/
│   ├── package.lua           Package model (OOP): load/normalize/resolve,
│   │                         layers + tombstones, dependency refs
│   ├── extractor.lua         Atomic .cap extraction (tmp dir + rename),
│   │                         encrypted-package decryption
│   ├── decrypter.lua         §6b envelope parsing + DEK unwrap + GCM decrypt
│   ├── composite.lua         §4a capsium:// refs + response processing
│   ├── store.lua             Package store scan + dependency resolution
│   ├── router.lua            Schema normalization + route auto-generation
│   └── security.lua          security.json parsing + SHA-256 + signature
│                             verification
├── auth/
│   ├── htpasswd.lua          htpasswd verification (apr1/{SHA}/crypt/bcrypt)
│   ├── basic.lua             HTTP Basic scheme
│   ├── session.lua           HMAC-SHA256 signed session cookies
│   ├── oauth2.lua            OAuth2 authorization-code + PKCE flow logic
│   └── access.lua            Dataset accessControl evaluation (401/403)
└── adapters/
    ├── nginx.lua             fs/zip adapters (LuaFileSystem + lua-zip)
    └── hash.lua              SHA-256 (resty.sha256 in OpenResty,
                            pure-Lua fallback elsewhere)

lua/capsium/                  Nginx glue (only code that touches ngx)
├── init.lua                  Entry point: wires adapters into the core,
│                             request handling, introspection API
├── config.lua                config.json loading + mount resolution
└── auth_gate.lua             §4b glue: challenges, OAuth2 redirects +
                              callbacks, session cookies, resty.http
----

The core never references `ngx`; the glue never implements domain logic.
Other platforms can plug in their own fs/zip/hash adapters.

.Crypto backend
[NOTE]
====
All RSA/AES operations go through `lua-resty-openssl` (FFI to the OpenSSL 3
`libcrypto` shipped in the pinned image — there is no `openssl` binary in
it, and `openssl enc` could not do AES-GCM anyway). Inside nginx workers
the symbols are already global; the Dockerfile symlinks
`libcrypto.so`/`libssl.so` so plain LuaJIT (busted) resolves them too.
`resty.openssl.version` is always required first (it performs the load).
====

.Request flow
[source]
----
HTTP Request
     │
     ▼
generic location /  ──►  capsium.handle_request()
     │                     ├─ resolve mount (Host + path prefix from config)
     │                     ├─ method check (GET/HEAD; OPTIONS w/ CORS)
     │                     ├─ capsium:// mounts: registry resolve (index.json,
     │                     │    newest satisfying semver, sha256 verify,
     │                     │    install into store — lazy, first request)
     │                     ├─ reactor:get_package(name)
     │                     │    ├─ decrypt (§6b, when encrypted + key configured)
     │                     │    ├─ extract .cap (atomic, verify SHA-256 + signature)
     │                     │    ├─ load package (metadata/manifest/routes/storage)
     │                     │    └─ resolve + mount dependencies (§4a store)
     │                     ├─ auth gate (§4b: basicAuth / OAuth2, when
     │                     │    authentication.json enables it)
     │                     ├─ package:resolve(subpath)
     │                     │    ├─ storage layers top→bottom, tombstones 404
     │                     │    └─ capsium:// dependency refs, exported only
     │                     ├─ dataset accessControl → 401/403
     │                     └─ serve static file / dataset JSON
     ▼
location /api/v1/introspect ──► capsium.handle_introspection()
location /introspect/       ──► capsium.handle_reactor_introspection()
location /package/          ──► capsium.handle_package_introspection()
log_by_lua                  ──► capsium.record_request()
                                  (metrics counters + request ring buffer)
----

== Package schemas

Both canonical and legacy forms are accepted and normalized on read
(see the Capsium architecture decisions document):

* `metadata.json` (required) — legacy array `dependencies` are normalized
to the canonical object form
* `manifest.json` — canonical `{"resources": {path: {type, visibility}}}`;
legacy `{"content": [{file, mime}]}` or `{"content": {name: mime}}`.
When absent, the manifest is generated by scanning `content/`
* `routes.json` — canonical `{"index": ..., "routes": [{path, resource |
dataset}]}`; legacy array or object forms with `target.file`
(content-relative). When absent, routes are auto-generated:
** `index` → `content/index.html` (also routed at `/`)
** every manifest resource under `content/` routed relative to `content/`
** HTML files get dual routes: `/page` and `/page.html`
** every dataset gets `/api/v1/data/<id>`
* `storage.json` — canonical `{"storage": {"dataSets": {...}}}`;
legacy `{"datasets": [{name, source, format, schema}]}`. Dataset sources
are served as JSON (`.json` served as-is, `.csv` converted to JSON
objects). YAML and SQLite datasets are not supported by this reactor
* `security.json` — when present, every listed file's SHA-256 is verified
at extraction; the package is *rejected* on mismatch (5xx with reason).
`content-validity` reports the verification result

== Digital signatures (§6a)

When `security.json` declares `digitalSignatures`:

[source,json]
----
{ "security": {
    "integrityChecks": { "checksumAlgorithm": "SHA-256", "checksums": {} },
    "digitalSignatures": { "publicKey": "signature.pub.pem",
                           "signatureFile": "signature.sig" } } }
----

the reactor verifies `signature.sig` at extraction: the signed payload is
the concatenation, in sorted checksum-key order, of the bytes of every
checksum-covered file (identical construction to the Ruby gem and the
standard, so `openssl dgst -sha256 -verify` agrees). The embedded public
key (or X.509 certificate) travels inside the package and is itself
covered by the checksums. Packages with a declared but non-matching
signature are rejected, same gate as checksums; `content-validity`
reports the signature result.

== Encrypted packages (§6b)

An encrypted `.cap` is a zip containing `metadata.json` (cleartext),
`signature.json` (the encryption envelope) and `package.enc` (the
AES-256-GCM ciphertext of the inner, plaintext `.cap`). When the layout
is detected at extraction, the reactor unwraps the RSA-OAEP-SHA256
(MGF1-SHA256) data-encryption key with the configured private key,
decrypts the inner zip, and proceeds exactly as with a plaintext package
(integrity and signature verification included).

The key is configured reactor-wide and/or per mount:

[source,json]
----
{
  "encryption": { "privateKeyPath": "/etc/capsium/keys/private.pem" },
  "mounts": [
    { "package": "secret-1.0.0.cap", "path": "/secret",
      "options": { "encryption": { "privateKeyPath": "/keys/other.pem" } } }
  ]
}
----

With no key configured (or an unreadable/wrong key), the package is
rejected with a clear 5xx reason. Extraction caching carries the key
identity: a package is never served from an extraction produced under a
different key (change the key and the package is re-decrypted on the next
request).

== Layered storage (§5a)

`storage.layers` (bottom → top) overlays package-relative directories
onto the content tree:

[source,json]
----
{ "storage": { "layers": [
    { "path": "base",    "writable": false, "visibility": "exported" },
    { "path": "updates", "writable": true,  "visibility": "private" } ] } }
----

* Requests resolve against the layers *top → bottom*; the first hit wins
(so `updates/content/index.html` shadows `base/content/index.html`).
Without a `layers` config the package root is the single implicit layer.
* Deletions are tombstones: a JSON array of merged-view paths in a
layer's `.capsium-tombstones` file. A path tombstoned at or above the
first serving layer resolves 404 (a file sharing a layer with its
tombstone still wins).
* `visibility: private` layers are not exposed to dependent packages
(see composite packages).
* Serving is read-only: no write API yet.

== Composite packages (§4a)

`metadata.dependencies` maps a dependency GUID to a semver range:

[source,json]
----
{ "dependencies": { "capsium://example.com/vendor-core": ">=1.0.0" } }
----

On activation, each dependency resolves against the *package store* —
a directory (`store_dir`, default `/var/lib/capsium/store`, overridable
via `CAPSIUM_STORE`) of `<name>-<version>.cap` files plus an optional
`index.json` (guid → file). The newest satisfying version wins
(exact/wildcard/comparator/caret/tilde ranges, AND-ed lists; `*` matches
any). Dependencies are extracted (with full integrity verification) and
mounted recursively; cycles and unsatisfiable ranges fail the package
with a clear reason.

Dependency content is reachable through `capsium://` route references
(route inheritance per 05x-routing):

[source,json]
----
{ "path": "/vendor/app.js",
  "resource": "capsium://example.com/vendor-core/content/app.js" }
----

* Only `exported` manifest resources are visible; referencing a
`private` resource of a dependency is an error, and private layers (§5a)
are invisible to dependents.
* `remap` is the effective served path (the original path stops
matching).
* `responseHeaders` are added only when absent;
`responseRewrite.headers` override; `responseRewrite.body` replaces the
served body.
* `requestHeaders` are accepted and ignored for static resources — they
only take effect when forwarding to dynamic handler routes, which this
reactor answers `501` (§4a handler contract).

== Static registry pull

A *static registry* is a directory or a static https base URL holding an
`index.json` plus `.cap` files relative to the registry root, so any
static host (GitHub Pages, S3, nginx) can serve it:

[source,json]
----
{ "packages": { "<guid>": { "name": "story-of-claire",
    "versions": { "1.0.0": { "file": "story-of-claire-1.0.0.cap",
                             "sha256": "<hex>", "size": 642047 } } } } }
----

A mount whose `package` is a `capsium://<guid>` reference is resolved
against the registry index at request time (lazy — cosocket HTTP is
unavailable in nginx init context): the newest version satisfying the
mount's semver range (`"version"`, default `"*"`) is downloaded,
verified against the index sha256 and installed into the package store
as `<name>-<version>.cap`, then served through the normal mount flow.
A store file already matching the index is reused as-is, so restarts do
not re-download. Remote registries require https (plain http is
accepted for loopback hosts only); redirects are followed (≤5) with the
scheme revalidated on every hop.

[source,json]
----
{ "registry": "/var/lib/capsium/registry",
  "mounts": [
    { "package": "capsium://fixtures/registry-app",
      "path": "/registry-app",
      "version": ">=1.0.0" } ] }
----

* The registry reference comes from the mount's `"registry"`, else the
reactor-level `"registry"`, else `CAPSIUM_REGISTRY` — a mount with a
`capsium://` source and no registry is a startup error (logged at init)
and answers a typed 5xx.
* The store directory is the mount's `"store"`, else `store_dir`
(`CAPSIUM_STORE`).
* Failures are typed and answered 5xx with the reason:
`not_configured`, `invalid`, `not_found`, `unsatisfiable`,
`checksum_mismatch`, `fetch` (the Ruby `RegistryError` hierarchy).

== Authentication (§4b)

A package ships `authentication.json`:

[source,json]
----
{ "authentication": {
    "basicAuth": { "enabled": true, "passwdFile": "auth/.htpasswd",
                   "realm": "capsium" },
    "oauth2": { "enabled": true, "provider": "google",
                "clientId": "...",
                "authorizationUrl": "https://.../authorize",
                "tokenUrl": "https://.../token",
                "userinfoUrl": "https://.../userinfo",
                "redirectPath": "/auth/callback",
                "scopes": ["openid", "email"] } } }
----

When any method is enabled, every package route requires authentication
(introspection stays open).

*Basic auth* is verified Lua-side against the htpasswd file (the
config-driven architecture mounts everything through one generic
location, so per-location `auth_basic` directives cannot express it —
the check matches what `auth_basic_user_file` accepts on this platform).
Supported hash formats: `$apr1$` (Apache MD5, htpasswd default),
`{SHA}`, and the `crypt(3)` family (`$2y$`/`$2b$` bcrypt, `$1$`, `$5$`,
`$6$`, DES). `passwdFile` is package-relative or absolute. Missing or
invalid credentials get `401` + `WWW-Authenticate`.

*OAuth2* implements the authorization-code flow with PKCE (S256) against
the configured endpoints: unauthenticated requests redirect to the
provider with state + verifier in a signed short-lived cookie (no
server-side state — any worker can complete the flow); the callback
verifies state, exchanges the code (`resty.http`), fetches userinfo and
sets an HMAC-SHA256 signed session cookie. *Secrets come from the
deployment, never the package*: `authentication.sessionSecret` and
`authentication.oauth2.clientSecret` in `config.json`, overridable via
`CAPSIUM_SESSION_SECRET` / `OAUTH_CLIENT_SECRET`. `sessionTtl` defaults
to 3600 seconds. When OAuth2 is enabled without a session secret the
reactor answers a clear 5xx. Cosocket DNS comes from a `resolver`
directive the container entrypoint renders from `resolv.conf`.

*Dataset access control*: route-level `accessControl` is enforced after
authentication — `authenticationRequired: true` maps to `401`,
`roles: [...]` maps to `403` unless the principal holds one. Basic-auth
principals carry no roles (htpasswd has none), so role-gated routes fail
closed under basic auth; OAuth2 roles come from `userinfo.roles`.

== Configuration

Configuration is read from `$CAPSIUM_CONFIG_PATH`, else the first existing
of `/etc/capsium/config.json`, `/etc/capsium/nginx/config.json`,
`/var/lib/capsium/config.json`, `./config.json`.

.Example `config/config.json`
[source,json]
----
{
  "package_dir": "/var/lib/capsium/packages",
  "extract_dir": "/var/lib/capsium/extracted",
  "cache_enabled": true,
  "cache_ttl": 3600,
  "log_level": "info",
  "mounts": [
    {
      "package": "mn-samples-iso-0.1.0.cap",
      "path": "/app",
      "domain": "example.com",
      "options": {
        "cache_ttl": 7200,
        "headers": {
          "X-Frame-Options": "SAMEORIGIN",
          "X-Content-Type-Options": "nosniff"
        }
      }
    },
    {
      "package": "api-1.0.0.cap",
      "path": "/api",
      "options": {
        "cors": {
          "allowed_origins": ["https://example.com"],
          "allowed_methods": ["GET"],
          "allowed_headers": ["Content-Type"],
          "max_age": 600
        }
      }
    }
  ]
}
----

Top-level keys:

`package_dir`:: Directory containing `.cap` files
(default `/var/lib/capsium/packages`)

`extract_dir`:: Extraction target (default `/var/lib/capsium/extracted`)

`cache_enabled`:: Use the `capsium_cache` shared dict to cache
introspection responses (default `true`)

`cache_ttl`:: TTL in seconds for the shared-dict cache (default `3600`)

`packages_config_dir`:: Optional directory with per-package `<name>.json`
mount configs (merged with `mounts` at startup)

`store_dir`:: Package store directory for composite packages (§4a;
default `/var/lib/capsium/store`, `CAPSIUM_STORE` env overrides)

`registry`:: Default static package registry (directory path or https
base URL) for `capsium://` mount sources; `CAPSIUM_REGISTRY` env
overrides, per-mount `"registry"` wins

`encryption`:: Reactor-level decryption key for encrypted packages (§6b):
`{"privateKeyPath": "/path/to/private.pem"}`

`authentication`:: Deploy-time authentication secrets (§4b, never from
packages): `sessionSecret` (required for OAuth2 sessions),
`sessionTtl` (default 3600), `oauth2.clientSecret`. Env overrides:
`CAPSIUM_SESSION_SECRET`, `OAUTH_CLIENT_SECRET`

Mount entries:

`package`:: Package filename (`.cap` extension optional), or a
`capsium://<guid>` registry reference (see *Static registry pull*)

`path`:: Mount path prefix (default `/capsium/<package-name>`)

`version`:: Semver range for `capsium://` mount sources (default `"*"`)

`registry`:: Per-mount registry override for `capsium://` sources

`store`:: Per-mount package store override for `capsium://` sources

`domain`:: Virtual host. Advisory: the mount answers on all hosts, and is
preferred for the named host when mounts overlap

`options.cache_ttl`:: Static `Cache-Control` max-age override for this
mount (default `31536000` → `public, max-age=31536000`)

`options.headers`:: Extra response headers applied to every response from
this mount (an explicit `Cache-Control` here wins over `cache_ttl`)

`options.encryption`:: Per-mount decryption key override (§6b):
`{"privateKeyPath": "/path/to/key.pem"}`. Extraction caching is keyed by
the effective key, so the same package may be mounted with different keys

`options.cors`:: CORS policy: `allowed_origins` (array, `*` supported),
`allowed_methods`, `allowed_headers`, `expose_headers`, `max_age`.
Preflight `OPTIONS` requests are answered with `204` when CORS is
configured.

Every package in `package_dir` is always also available at
`/capsium/<package-name>` without configuration. `/api/v1/introspect`,
`/introspect` and `/package` are reserved.

Package routes are GET-only: other methods receive `405`
(`Allow: GET, HEAD`); HEAD is served like GET without a body. Dynamic
`handler` routes are accepted by the parser but answered with `501`.

== HTTP API

Package serving:: routes from the package under its mount point.

Introspection (GET only)::

`/api/v1/introspect/metadata`::: `{packages: [{name, version, author,
description}]}`

`/api/v1/introspect/routes`::: `{routes: [{package, routes: [{method,
path}]}]}`

`/api/v1/introspect/content-hashes`::: `{contentHashes: [{package,
hash}]}` — SHA-256 of the `.cap` blob

`/api/v1/introspect/content-validity`::: `{contentValidity: [{package,
valid, lastChecked, reason?}]}` — actual integrity verification result

Reactor-level introspection (GET only)::

`/introspect/status`::: `{status: "running", uptime, packagesLoaded}` —
`packagesLoaded` counts the configured mounts

`/introspect/config`::: `{mounts, registry, storeDir, cache: {enabled,
ttl}, authEnabled}` — built from a whitelist: deploy secrets
(`authentication.*`) and key material (`encryption.privateKeyPath`) are
never exposed, and registry URL userinfo is redacted

`/introspect/metrics`::: `{uptime, requestsTotal, requestsByStatus}` —
shared-dict counters over every Lua-handled request

Per-package introspection (GET only, 404 for unknown names)::

`/package/<name>/status`::: `{package, version, status: "loaded",
valid}` — `<name>` is the package metadata name

`/package/<name>/metadata`::: `{name, version, description, author,
guid}`

`/package/<name>/logs`::: `{package, logs: [line, ...]}` — recent lines
of a per-worker ring buffer (oldest first, `"<ISO8601> <METHOD> <uri>
-> <status>"`); `?lines=N` clamps to 1..1000 (default 100)

Non-GET methods on all of these receive `405` (`Allow: GET`); the
per-package endpoints apply the CORS policy of the mount serving the
package.

All introspection endpoints lazily extract and load packages on demand:
a freshly started reactor reports every `.cap` in `package_dir`.

== Running with Docker

[source,bash]
----
docker build -t capsium-nginx .
docker run -d -p 8080:80 \
  -v $PWD/packages:/var/lib/capsium/packages \
  -v $PWD/config:/etc/capsium \
  capsium-nginx
----

Or with docker compose (`docker-compose up -d`).

The base image is pinned: `openresty/openresty:1.27.1.2-12-alpine-fat`
(see the `BASE_IMAGE` arg in the `Dockerfile` and the `Rakefile`).

== Testing

All Lua tooling runs in Docker; the RSpec integration suite runs on the
host against the Dockerized reactor.

Lua unit tests (busted) and lint (luacheck)::

[source,bash]
----
docker build -t capsium-nginx:test .
docker run --rm -v $PWD:/src -w /src capsium-nginx:test sh -c \
  'luarocks install busted && luarocks install luacov && busted --verbose'
docker run --rm -v $PWD:/src -w /src capsium-nginx:test sh -c \
  'luarocks install luacheck && luacheck lib lua test'
----

(or `rake lua:test` / `rake lua:lint`)

Integration suite (RSpec, needs Docker + Ruby)::

[source,bash]
----
bundle install
bundle exec rake ci     # builds fixtures + image, starts container, runs specs
----

`rake fixtures` regenerates the generated `.cap` test fixtures via
`spec/fixtures/build_fixtures.rb`:

* `canonical-sample` (+tampered variant) — canonical schemas +
`security.json`
* `signed-sample` (+bad-signature variant) — §6a digital signatures
* `encrypted-sample` — §6b envelope + AES-256-GCM inner zip
* `layered-sample` — §5a layers + tombstones
* `composite-sample` + `store/vendor-core` (two versions) — §4a store
* `auth-sample` (basicAuth, four htpasswd hash formats) and
`oauth-sample` (OAuth2 + PKCE against the mock provider)
* `multi-test`, `dormant-package` — legacy/cold-start fixtures
* `registry/` — static registry fixture (index.json + `.cap` files):
`registry-app` 1.0.0/1.1.0 (semver-newest + store-reuse tests) and
`registry-tampered` (wrong index sha256 → install rejected)

Test-only RSA keys are generated into `spec/fixtures/keys/` on each run.
The OAuth2 integration spec serves a WEBrick mock provider (the suite
verifies the PKCE S256 challenge server-side); the container reaches it
via `host.docker.internal`. The `mn-samples-iso-0.1.0.cap` fixture is a
real legacy-format package.

Useful rake tasks: `rake docker:start|stop|restart|logs|shell`,
`rake spec`, `rake test`, `rake clean`.
